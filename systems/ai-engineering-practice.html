AI 辅助的专利文档修正与自动化工具链踩坑

这次的任务是为一份中文发明专利补充参数定义。专利代理想让我逐条回应 27 条审阅批注，每条批注的核心诉求都是同一个："这个参数什么意思，请补充定义"。看似简单的工作，实际做下来涉及了 OOXML 操作、文档知识交叉验证、工作流工具的边界限制、以及文件操作的容错。以下记录全过程中的经验和踩坑。

一、OOXML Track Changes 的直接操作

专利审查要求使用 Word 的"审阅-修订模式"（Track Changes），即所有修改必须以 <w:ins> 和 <w:del> 的形式标记，不能做静默替换。

第一个坑：python-docx 虽然能读写段落、样式和表格，但它不保留 Track Changes 标记。如果用它打开一个包含修订痕迹的 docx，然后保存，所有的 <w:ins> / <w:del> 会被识别为普通文本，修订全部丢失。所以必须直接操作 OOXML 的原始 XML。

正确的做法：用 lxml 解析 word/document.xml，构造 <w:ins> 元素插入到对应段落末尾。每个 <w:ins> 需要包含唯一的 w:id、作者名、时间戳、以及带格式（红色下划线）的 <w:r> 子元素。

<w:ins w:id="3" w:author="haiy1" w:date="2026-06-03T09:00:00Z">
  <w:r>
    <w:rPr>
      <w:color w:val="FF0000"/>
      <w:u w:val="single"/>
    </w:rPr>
    <w:t> a_q：第q个双平面单元的两块导体板之间的半间距</w:t>
  </w:r>
</w:ins>

第二个坑：Word 文档中，批注的锚定方式有两种：<commentRangeStart> + <commentRangeEnd> 包裹被评注的文本，或者直接使用 <commentReference>。如果只检查 commentRangeStart，会漏掉只用 commentReference 锚定的批注。实际遇到的情况是 27 条批注中有 3 条只用了 commentReference。

二、ZipFile 写模式的截断陷阱

这是整个过程中最大的一次事故。

错误写法：

with zipfile.ZipFile(docx_path, 'w') as zout:        # w 模式：此刻文件已被截断为空
    with zipfile.ZipFile(docx_path, 'r') as zin:      # 读取已被截断的文件 → BadZipFile
        entries = {n: zin.read(n) for n in zin.namelist()}
    # ...写回...

zipfile.ZipFile('w') 在打开文件的一瞬间就会把原文件截断为 0 字节。此时如果还试图从同一个路径读取，只会得到空文件或报错。文件永久损坏。

正确写法：

# 先全量读入 dict
with zipfile.ZipFile(docx_path, 'r') as zin:
    entries = {n: zin.read(n) for n in zin.namelist()}
zin.close()

# 修改 entries 中的内容
entries['word/document.xml'] = modified_xml

# 再写入
with zipfile.ZipFile(docx_path, 'w', zipfile.ZIP_DEFLATED) as zout:
    for name, data in entries.items():
        zout.writestr(name, data)

关键原则：读和写分两步，先全量读入 dict 再写回，绝不开边读边写。

这次文件损坏后，原始备份又因为 WPS Office 的临时文件自动清理机制而丢失了。教训：在操作 docx 之前，一定要做显式的手动备份（cp），不要依赖 WPS 的 .~lock 临时文件。

三、参数定义的交叉验证

从 27 条批注映射出约 90 个参数后，必须用项目文档（docs/facts/）逐条验证定义的准确性。验证中发现了两类错误：

1. 缺失下标。 l_{1,g}、l_{2,g}、y_{\nu,g} 等参数只标了线圈族 g，但实际这些距离同时依赖单元编号 q。文档中一致使用 l_{1,g,q}、l_{2,g,q} 等完整双下标。且专利同一段落中 a_q 已经带了 q 下标，l 和 y 不带则前后不一致。

2. 术语错误。 线圈板面的方向描述使用了"上板/下板"，但项目坐标系采用 front_back 语义（y 轴法向，前板在 +y、后板在 -y）。正确术语应为"前板/后板"。这个问题不仅出现在注入的参数定义中，也出现在专利正文的镜像法段落里。

验证方法：将每条定义与 docs/facts/ 中的权威描述对照，检查符号、公式、物理含义是否一致。参数去重用符号的精确匹配（含下标），不模糊合并。

四、hy-workflow 工具链的边界

4.1 hy_commit 无法指定 PR 目标分支

hy_commit 只接受 title 和 body 两个参数，内部调用 gh pr create 时不传 --base，导致 PR 始终打到 GitHub 仓库的默认分支（main）。当项目存在 dev 作为活跃开发主线、main 作为稳定分支时，hy_commit 无法满足"PR 到 dev"的需求。

绕过方式：手动 gh pr create --base dev，跳过 hy_commit 步骤。已向 hy-workflow-mcp 提 issue 建议增加 base 参数。

4.2 .hy/workflow.json 导致的分支切换冲突

.hy/workflow.json 是 hy-workflow 在项目根目录生成的临时文件，记录当前工作流阶段。当这个文件被手动删除后，通过 git checkout 切换分支时会因为跟踪状态冲突而失败。原因是 .hy/ 目录在某些分支被跟踪、某些分支不被跟踪，导致 checkout 时 git 需要覆盖或保留该文件。

解决：rm -rf .hy/ 后立刻 git checkout -b new-branch，趁工作流状态文件还没被重新创建。

4.3 工作流状态机卡住

手动操作 git（如 git stash、git checkout、git branch -D）会导致 hy-workflow 的状态机与实际 git 状态脱节。出现类似 "Phase 'init' is not in [approve, branch]" 这样的错误提示。

恢复方式：hy_reset 重置到 plan 阶段，重新走 plan → approve → branch → edit → verify 流水线。如果 hy_reset 也失效，删除 .hy/workflow.json 或 .hy/ 目录后再调用 hy_plan。

五、正文修改也需要修订模式

专利正文（非批注注入部分）的修改同样不能做静默替换。例如将镜像法段落中的"上板与下板镜像坐标取平均"改为"前板与后板镜像坐标取平均"，需要拆解原来的 <w:r> 文本为三部分：前缀 + <w:del>旧文本</w:del> + <w:ins>新文本</w:ins> + 后缀。

这要求在 <w:r> 元素级别操作 XML，将原 run 替换为拆分后的多个 run 元素。用 lxml 的 parent.remove() + parent.insert() 可以做到。

七、核心经验

  1. 操作 docx XML 时，先全量读入 dict 再写回。边读边写 = 文件截断 = 永久损坏。
  2. 在 zip 操作前做显式 cp 备份。不要依赖 WPS 的 .~lock 临时文件，它随时可能被清理。
  3. python-docx 不保留 Track Changes。任何需要修订模式的操作，只能用 lxml 直接操作原始 XML。
  4. 批注锚定有两种格式。仅检查 commentRangeStart 会漏掉纯 commentReference 的批注。
  5. 参数定义必须与项目文档交叉验证。不能仅依赖脚本输出，必须人工（或自动化）对照 docs 核实符号、下标、物理含义。
  6. 术语一致性要核对坐标系。上下/前后/左右不是随意选的，必须与项目采用的坐标语义一致。
  7. 正文修改也要用修订模式。不能对专利原文做静默替换，必须拆解 run 元素并包裹 del+ins。
  8. hy_commit 无 base 参数。PR 目标分支不是 dev 时，手动 gh pr create --base dev。
  9. hy-workflow 状态机脆弱。手动 git 操作后需要 hy_reset 恢复，或删除 .hy/ 目录重建。
